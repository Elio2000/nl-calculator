# 自然语言计算器

用中文说出算式，得到精确结果。

```
你：一加一等于几
答：等于二            1+1 = 2
```

## 这个项目做的是什么

**把中文口语翻译成已有计算器能理解的表达式，然后让它们去算。**

数学算法一个都不是我们写的——加减乘除、三角函数、高精度、复数、解方程、求导积分，全部来自
[mathjs](https://github.com/josdejong/mathjs) 和 [nerdamer-prime](https://github.com/together-science/nerdamer-prime)。
完整的引用与致谢见 **[CREDITS.md](CREDITS.md)**。

```
中文口语  ──我们写的──▶  规范表达式  ──mathjs / nerdamer──▶  结果
          翻译层                        计算层
       （规则 + LLM）                （开源项目）
```

这个定位决定了两件事：
- **能力边界**由计算层决定。它们算不了的，我们也算不了——边界在 [BOUNDARIES.md](BOUNDARIES.md) 里逐项列清楚了
- **测试重点**在翻译层。计算层的正确性由 mathjs 的 321 个测试文件保证，我们不重复测「2+3 等于几」，只测「『二加三』能否正确翻译成 `2+3`」。测试策略见 **[TESTING.md](TESTING.md)**

## 核心主张

**理解可以有歧义，计算不可以。**

自然语言天然模糊，数学结果不能模糊。所以这个项目把两件事彻底分开：

- **理解**这一层允许不确定。读法有多种就把候选列出来让人选，读不懂就交给 AI 翻译——但翻译结果仍然要人确认。
- **计算**这一层永远是本地、确定性、可验证的。AI 从不参与算数，它最多只能提议"这句话可能是这个算式"。

这条边界带来一个有用的性质：**模型再不靠谱，最坏结果也只是让用户多点一次「都不是」，而不会给出一个错的答案。**

## 它能做什么

```
一加一等于几              → 等于二
三与五的和乘以二           → 等于十六          (3+5)×2 = 16
负二的平方                → 等于四            (-2)^2 = 4
负的二的平方              → 等于负四          -(2^2) = -4
二的三次方的二次方         → 等于六十四        ((2)^3)^2 = 64
cos派加sin派              → 等于负一
e的100次方                → 约等于 2.68811714182 × 10⁴³
根号负四                  → 等于 2i
sin三十度                 → 等于 0.5          带「度」自动按角度制
以二为底八的对数           → 等于三
一百除以七的余数           → 等于二
三分之一                  → 等于 1/3，约 0.333333
一百打八折                → 等于八十
一百涨百分之十             → 等于一百一十
六除二                    → 两种读法，你选哪个？
解方程x平方加一等于零       → x = i，或 x = -i
x平方求导                 → 2·x
```

还支持连续对话与多步提问：

```
你：1+1等于几            → 等于二            1+1 = 2
你：那在这个基础上再乘以5  → 等于十            (1+1)·5 = 10
你：再加3呢              → 等于十三          (1+1)·5+3 = 13
你：三加五等于几          → 等于八            3+5 = 8      ← 完整句子，当作新题

你：1+2×3等于几？再乘5等于几？再加3等于几？
    → 三个步骤逐条作答：7 → 35 → 38（都对，不是让你二选一）
```

算式回显用 KaTeX 排版，分数是分数线、幂是上标，一眼能看出理解对没对。

还支持：语音输入（本地 Whisper，不需要 key）、AI 归一化（本地或远端模型）。

## 架构

```
文本 ──────────────┐
语音 → 本地 Whisper ┘
   ▼
中文 NLU（自研）
 ├─ 归一化   全半角、剥离多字填充词
 ├─ 分词     词表最长匹配 + 中文数字识别
 ├─ 意图分流 求值 / 解方程 / 求导积分
 ├─ 扁平模板 处理不连续三段式构式
 └─ 递归下降 优先级、就近绑定、「的」后缀
   ▼
规范表达式（mathjs 语法的白名单子集，全括号）
   ▼
唯一读法 → 直接算 ｜ 多种读法 → 候选卡 ｜ 读不懂 → AI 翻译 → 候选卡
   ▼
mathjs（四则/科学函数）｜ nerdamer-prime（方程/微积分，惰性加载）
   ▼
回答生成：修约、数字转中文、算式回显
```

### 什么是「规范表达式」

整个系统的中枢概念：**mathjs 语法的一个白名单子集**——显式乘号、完整括号、只允许固定的函数与常量，禁用赋值/索引/数组。

它同时是三样东西：规则层的输出目标、AI 归一化的输出契约、给用户看的算式回显。因为 AI 的输出必须过这道白名单校验，模型即使被诱导也无法让引擎执行越权构造。

## 自研 vs 复用

动手前调研了 12 个开源项目的源码，结论是**引擎全部复用，中文构式层必须自研**。

| 组件 | 来源 | 为什么 |
|---|---|---|
| 计算引擎 | mathjs (Apache-2.0) | BigNumber 模式一步同时解决 `0.1+0.2=0.3` 和科学函数；自带复数、精确分数、`^` 右结合、`toTex` |
| 方程/微积分 | nerdamer-prime (MIT) | JS 生态里唯一同时有通用 `solve`、符号积分、极限、数值求根的库。选分叉是因为上游主线停更于 2022，分叉仍在活跃维护 |
| 中文数字解析 | 移植 cn2an 规则 | 见下文 |
| 数字转中文 | nzh (BSD-2) | 字符串运算、无精度上限 |
| **中文构式层** | **自研** | 调研证明全球没有开源实现 |

### 为什么中文构式层没得抄

- **SoulverCore** 做到了简体中文自然语言计算，但是闭源二进制 + 商业授权
- **SymPy Gamma**（开源版 Wolfram Alpha）的自然语言层是**烂尾的死代码**，`derivative of x^2` 实际会被解析成 `diff(o*f*x**2)` 直接崩掉。它真正做的只是放松数学记法（`sin x` → `sin(x)`）
- **NoteCalc / recomputer / numr** 全是英文严格语法，其中 recomputer 作者自评"strict"，最不自然语言
- 三家开源 NL 计算器清一色是"带类型词法 → 优先级解析 → 十进制求值"，**无一使用 ML/LLM**

它们贡献的是架构思想，不是代码：notepad-based-calculator 的「词形算符表做成数据」、SoulverCore 的「中英语法叠加而非替换」、SymPy Gamma 的「规范形与显示形分离」。

### 词表是数据，文法是代码

`src/core/grammar/lexicon.json` 存词形算符、函数同义词、构式关键词——加一种说法通常只需加一行。

但**文法是手写的递归下降**（`parser.ts`），不是配置。因为优先级、就近绑定、递归这三件事模板表达不了。notepad-based-calculator 能用 JSON 模板做句式，恰恰因为它不处理递归和优先级。

## 三个决定文法形状的用例

**一、负号绑定**

```
负二的平方    = (-2)² = 4     「负二」是一个数
负的二的平方  = -(2²) = -4    「负」是一元运算符
```

隔着「的」与否决定了 `负` 归词法还是归运算符，这一对用例定死了 unary 与 power 的层次关系。

**二、链式幂必须全括号**

中文「二的三次方的二次方」是从左往右读的 `(2³)² = 64`，而 mathjs 的 `^` 是右结合。少一层括号就会被重新解读成 `2^(3²) = 512`——差 448。所以规范表达式一律输出全括号，让引擎无法重新理解。

**三、不连续三段式构式**

「以二为底八的对数」「一百除以七的余数」里的「的」不属于最近的操作数——它管的是整个前面的结构。递归下降的后缀前瞻看不到这种跨度，所以在文法之前加了一道**扁平模板 pass**，先把这类非递归构式整体消掉。

## 设计决策记录

**百分比在翻译层展开，不用引擎的 `%`。** mathjs 里 `50%(13)` 会被解析成取模得 11，不是「13 的 50%」。三家引擎的百分号语义还各不相同。所以「百分之二十」在翻译层就变成 `((20)/100)`，引擎只见显式除法。

**不照搬 libqalculate 的相对百分比语义。** 英文 `100 + 10% = 110`，但中文「一百加百分之十」的「加」是字面加法，就是 100.1。中文里真正表示相对变化的是「涨/降/打折」，只对这些做相对处理。

**偶次根走 `sqrt` 而非 `nthRoot`。** `nthRoot(-4,2)` 在 mathjs 里直接抛错，而 `sqrt(-4)` 会提升成 `2i`——与「根号负四」的行为保持一致。奇次根保留 `nthRoot`：`nthRoot(-8,3)` 给 `-2`，符合直觉，而 `(-8)^(1/3)` 会给复主根。

**整数结果不做有效数字修约。** `factorial(20)` 必须原样给出 2432902008176640000，若按 12 位修约会退化成 2432902008180000000——一个看似精确实则错误的数。

**含超越函数时才做零值吸附。** `sin(pi)` 在 64 位精度下算出 3.08e-64，这类误差要归零；但纯算术表达式不做这个处理，免得把用户真正输入的 `1e-60` 也抹掉。

**中文数字解析自研而非用微软识别库。** 实测 `@microsoft/recognizers-text-number` 的中文口语覆盖很好（20 例过 19），但它**静默猜测**——`百十一`→11、`十一十二`→22、`这是一段话`→1，而且 `三分之一` 会变成浮点 0.333333333333333，让引擎的精确分数能力白费。3.6MB 的通用 NLP 库换来一个会猜的数字层，不划算。移植 cn2an 的规则只有 400 行，而且**非法输入抛错不猜**。

**nzh 只用于反向。** 它的解析方向实测口语失败过半且全部静默出错（`一万二`→10002、`两千三`→3、`两`→0），一个都不抛异常。计算器给出"看起来像数字的错数字"比报错糟糕得多。

```bash
npm install
npm run dev
```

### 克隆后准备

**代码之外只有两样东西不在仓库里**，都是有意的：

| 东西 | 为什么不在仓库 | 怎么办 |
|---|---|---|
| 语音模型权重 `public/models/`（约 1.3GB） | 太大，git 装不下 | **什么都不用做。** 目录里有权重就全程离线；没有就首次用语音时自动从 HuggingFace 下载并进浏览器缓存，之后同样离线 |
| DeepSeek API key | 凭据绝不进仓库 | 想用内置转发就设 `DEEPSEEK_API_KEY`（见下文）；不设也能用——规则引擎完整可用，AI 归一化可切成直连或本地 Ollama |

模型那条是 `src/services/stt.ts` 里 `env.allowLocalModels` / `env.allowRemoteModels` 同时为 `true` 的效果：先找本地 `/models/`，404 就回落到远端。所以**同一份代码，有权重就是离线应用，没权重就是首次联网的在线应用**，不需要额外的下载脚本。

（想预先把权重拉到本地全离线，把 `Xenova/whisper-base`、`Xenova/whisper-small`、`onnx-community/whisper-large-v3-turbo` 三个仓库按同名目录放进 `public/models/` 即可，`onnx` 子目录取 `*_quantized.onnx`。）

```bash
npx vitest run
```

316 个测试。测试策略见 **[TESTING.md](TESTING.md)**——那篇讲的是「怎么验证这东西是对的」，包括为什么这个项目最该测的不是功能覆盖率，而是「绝不给出错误答案」这条不变量。

简要说，测试分六类：行为基线、从 cn2an/libqalculate 搬来的边界用例、词表覆盖（每个词条都必须有用例走到）、构式相邻边界（真实 bug 出没处）、属性测试（枚举组合断言性质）、bug 回归（每个手工发现的问题留一条）。

## 语音输入

**录音不离开本机**——Whisper 在浏览器里跑。`public/models/` 有权重就完全离线，没有则首次使用时从 HuggingFace 下载（见「克隆后准备」）。有 WebGPU 就用 WebGPU，没有自动回落 WASM。

实测中文数学短句（`node scripts/eval-voice.mjs base small turbo`，音频由 `scripts/make-audio.sh` 用系统 TTS 合成）：

| 档位 | 端到端算对 | 单次推理 | 典型输出 |
|---|---|---|---|
| base 78MB | 1/5 | ~0.4s | 「三点五乘以负二」→「3.5成以负2」 |
| small 259MB | 0/5 | ~1.0s | 「根号九是多少」→「更耗久事多少」 |
| **turbo 1GB** | **4/5** | ~3.0s | 「二的三次方」→「2的三次方」✓ |

默认用 turbo。这里衡量的是**端到端算得对不对**，不是文本一字不差——Whisper 把「一加一」写成「1加1」完全无害，构式层本来就支持中阿混写。

turbo 唯一失败的「根号九」→「根号酒」是同音字错误，正好是 AI 归一化该接手的场景。

**识别结果填进输入框，不自动发送**——识别难免出错，让人看一眼、改一改再回车。

## LLM 后端（DeepSeek）

后端是任意 OpenAI 兼容服务。默认走**同源转发**——浏览器不直接碰第三方服务，也就不需要用户填 key：

```
浏览器 ──POST /api/llm/v1/chat/completions──▶ 本站服务端 ──加 Authorization──▶ api.deepseek.com
        （同源，页面里没有任何凭据）           （key 只在这里）
```

服务端在开发时是 vite 代理（`vite.config.ts`），部署时是 `scripts/serve.mjs`；两边同一套约定：key 从环境变量 `DEEPSEEK_API_KEY` 读，读不到就读项目根目录的 `.deepseek.key`（已在 `.gitignore` 里）。**没有 key 时转发路由返回 500 并说明原因，绝不把没有认证的请求转出去。**

```bash
export DEEPSEEK_API_KEY=sk-xxxx      # 或：echo sk-xxxx > .deepseek.key
npm run dev
```

设置面板里有三个预设，点一下就换后端：

| 预设 | 服务地址 | 模型 | 要不要填 key |
|---|---|---|---|
| **内置转发**（默认） | `/api/llm/v1` | `deepseek-v4-flash` | **不用**，凭据在服务端 |
| DeepSeek 直连（BYOK） | `https://api.deepseek.com/v1` | `deepseek-v4-flash` | 要，自备；只存在本机浏览器 |
| 本地 Ollama | `http://localhost:11434/v1` | `qwen2.5:1.5b` | 不用，但要 `OLLAMA_ORIGINS='*' ollama serve` |

直连之所以可行，是因为 DeepSeek 的接口允许跨域；换成不开 CORS 的服务就只能走转发。要更强的模型把模型名换成 `deepseek-v4-pro` 即可。不想用 AI 就在设置里选「不启用」，规则引擎照常工作。

调用时机有两种，也在设置里切：
- **规则优先**（默认）：规则能解析的直接算——毫秒级、离线、同样输入得到同样结果；解析不了时才调模型
- **LLM 翻译优先**：一律先由模型翻译，规则作为退路。覆盖面更广，代价是每次都要等模型响应

无论哪种，**算数始终由本地引擎完成**。

实测见 [TESTING.md](TESTING.md#llm-翻译实测)：14 条用例（基础对照 / 语音同音字 / 口语绕弯 / 真歧义 / 解方程求导积分 / 非数学输入拒答），`deepseek-v4-flash` 全过。复跑：

```bash
node scripts/eval-llm.mjs                                          # DeepSeek，key 从环境读
node scripts/eval-llm.mjs --base-url http://localhost:11434/v1 --model qwen2.5:1.5b
```

其中最有意思的一条是**语音同音字纠错**——system prompt 里明确告诉模型输入可能来自语音识别，
并给了几个谐音例子。整条链路：

```
语音「根号九是多少」
  → Whisper 听成「根号酒是多少」
  → 规则引擎读不懂（cause=comprehension，才会转交 AI）
  → AI 提议 sqrt(9)，说明「酒」应该是「九」
  → 用户点选
  → 本地引擎算出 3
```

第四步算出 3 的是本地引擎，不是模型——模型全程只提议了 `sqrt(9)` 这个读法。

**模型大小是有差别的。** 同一套 14 条用例，本机 `qwen2.5:1.5b` 只过 6 条（2026-07-30 实测）：
符号计算、真歧义要给两个候选、括号规范性（「五的立方再开平方」写成 `(5)^3^(1/2)`，被右结合读成
16.24 而不是 11.18）都是它的短板。所以默认接的是云端 flash 档，本地小模型作为「完全离线」这个
需求下的备选——**它给错也只是多一次「都不是」，不会变成一个错答案。**

不启用时规则引擎完整可用，只是读不懂的句子会直接说读不懂。

## 部署与预览

给别人试用（例如面试演示）：构建产物 + 一个零依赖的预览服务器，再用 ngrok 打洞。

```bash
npm run build
DEEPSEEK_API_KEY=sk-xxxx npm run serve       # 默认 4173 端口，PORT 可改
ngrok http 4173
```

`scripts/serve.mjs` 做两件事：静态伺服 `dist/`，以及把 `/api/llm/v1/chat/completions` 转发给
DeepSeek 并注入 Authorization。**对方打开链接就能用 AI 归一化，不用填任何 key。**

这个洞会暴露在公网上，所以转发是一条白名单而不是一个通道：只认那一个路径、只认 `deepseek` 开头的
模型、请求体限 64KB、`max_tokens` 封顶 4096，其余请求一律 404（细节与自测见 [BOUNDARIES.md](BOUNDARIES.md)）。

远程访问时**建议在设置里把语音模型切到 base 档**：turbo 是 1GB，走 ngrok 隧道首次加载会很久。

## 已知限制

- 名词形分组只支持简单操作数（`三与五的和`），更复杂的嵌套会干净地失败并走候选/兜底，而不是猜
- 一句话里出现多个裸「除」时直接拒绝（候选会组合爆炸），提示用户改说「除以」
- 方程限一元；符号微分方程需要 SymPy 级 CAS，JS 生态没有（架构上可由 Pyodide 补，未实现）
- 未做求极限：中文「x 趋近于零时的极限」是个不小的构式，没有半成品配置留在词表里
- 浏览器**直连** LLM 服务需要对方允许跨域（DeepSeek 允许，Ollama 需设 `OLLAMA_ORIGINS`）；默认的同源转发没有这个问题
- 内置转发要求服务端配好 `DEEPSEEK_API_KEY`，纯静态托管（GitHub Pages 之类）用不了这条链路，只能 BYOK 直连
- 语音需 https 或 localhost 环境
